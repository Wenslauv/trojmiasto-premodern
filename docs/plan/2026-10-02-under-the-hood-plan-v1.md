# План доработок «под капотом» — 2026-10-02 (v1)

Источник: анализ кода и данных в сессии 2026-10-02.
Статус: Draft (ждёт ответов на открытые вопросы).
Ветка: `single_data_sources`.

## Контекст

Переход на БД сейчас не нужен: данных мало (11 событий, ~125 КБ), сайт только читает данные, вносит их один человек, а git даёт историю правок, ревью и бесплатный хостинг на Pages. Проблемы не в формате JSON, а в отсутствии нормализации и в дублировании логики:

- `events.json` и `events/*.json` разошлись: 7 из 11 файлов отличаются (названия событий; в 17.08 колода Standstill, в `events.json` уже Landstill).
- Один игрок под двумя ID: Wiaczasłau Kukhtsiuk (p02, p10), Wojciech Ćwikliński (p03, p11). Фронт склеивает игроков по нормализованному имени.
- Цвета колод хранятся в каждой строке и расходятся: Replenish UW/WU, Landstill UW/WU, Darigaaz Midrange RBG/BRG, Quiet Tribe GWUR/GWUr.
- Логика статистики продублирована в `scripts/generate-data.mjs` и `src/lib/data.ts`.
- Клиент грузит весь `events.json` и пересчитывает игроков в браузере; `players.json` и `events-summary.json` генерируются, но не используются.
- `vite build` не проверяет типы, тестов нет.
- ID событий в двух форматах.

Когда БД станет оправдана: живые паринги, аккаунты игроков, несколько организаторов, вносящих результаты без git.

## Правила выполнения

- Каждый шаг — отдельные коммиты по AGENTS.md (одна логическая единица на коммит).
- После каждого шага сайт рабочий: `npm run build`, `npm test`, `npm run check-data` проходят.
- После любого завершённого шага ветку можно вливать в `main`.

## Steps

1. Страховочная сетка.
Зависит: нет.
Включает:
- `"build": "tsc --noEmit && vite build"`, чтобы CI ловил ошибки типов;
- vitest: тесты на `matchWinPercent` (ничья = 0.5), `effectiveMatchRecord` (BYE не учитывается), склейку игроков;
- снимок ключевых цифр на текущих данных (винрейты игроков, матчапы), чтобы следующие шаги не меняли результаты незаметно;
- `npm test` в CI перед сборкой;
- ESLint + Prettier (форматирование — отдельным коммитом `style:`).

2. Единый источник данных.
Зависит: шаг 1.
Включает:
- синхронизировать `events/*.json` с `events.json` (в `events.json` более новые правки) — коммит `data:`;
- канон — один файл на событие; `events.json` собирается скриптом и становится генерируемым;
- исходники вынести из `public/` в `data/`, чтобы в деплой попадали только сгенерированные файлы;
- входящие файлы (`incoming_*.json`) — в отдельную папку `data/incoming/`, чтобы сборка их не подхватывала;
- перевести `add-event`, `add-event-compact`, `update-event`, `export-event`, `generate-data` на новую раскладку.

3. Реестры игроков и колод.
Зависит: шаг 2.
Включает:
- `data/players.json`: `{ id, name, aliases[] }`;
- ID игрока — имя и фамилия латиницей (`marcin-kowalski`), задаётся один раз и не меняется; при исправлении написания меняется только `name`; полный тёзка получает суффикс `-2`;
- инициалы (`MK`) — сокращения для ручного ввода в `aliases`; неоднозначное сокращение (сейчас `AM`, `MB`) — ошибка импорта с просьбой уточнить, без угадывания;
- склеить дубликаты ID в событиях — коммит `data:`: p02 + p10 → `wiaczaslau-kukhtsiuk`, p03 + p11 → `wojciech-cwiklinski`;
- скрипт `npm run rename-player -- <old> <new>`: меняет ID в реестре и во всех событиях одной командой (например, `marek-palub` → `marek-palubski`); валидация проверяет, что старый ID нигде не остался;
- предупреждение импорта на обрезанные имена (оканчиваются на `...` или `…`) — из-за обрезанного `Wojciech Ć...` и появился p11;
- `data/decks.json`: `{ id, name, colors, aliases[] }`, сюда же переносится `config/matchup-deck-rules.json`;
- цвета колод только из реестра, единый порядок WUBRG, строчные буквы — сплэш;
- валидация: неизвестный игрок или колода — ошибка `check-data`; импортёр резолвит имена через `aliases`;
- фронт определяет игрока только по ID, склейка по имени удаляется.

4. Общий модуль статистики и расчёт на билде.
Зависит: шаг 3.
Включает:
- чистые функции статистики в одном TS-модуле; скрипты переводятся на TS (запуск через `tsx`);
- на билде генерируются: индекс событий, `event/<id>.json`, список игроков, `player/<id>.json` (с deckStats), матчапы;
- `src/lib/data.ts` становится тонким слоем загрузки готовых файлов;
- неиспользуемые `players.json` / `events-summary.json` заменяются новыми файлами;
- тесты из шага 1 переносятся на новый модуль, снимок цифр не должен измениться (кроме ожидаемых изменений шага 3).

5. Стабильные ID событий.
Зависит: шаг 2.
Включает:
- формат `YYYY-MM-DD-<place>-<type>`, например `2026-09-21-sidequest-weekly`; при совпадении — суффикс `-2`;
- имена файлов совпадают с ID.

6. Схема данных на zod.
Зависит: шаг 4.
Включает:
- одна схема вместо `scripts/lib/events-validation.mjs` + `src/types.ts`; TS-типы выводятся из схемы;
- проверки ссылок между файлами (события → реестры игроков и колод).

7. Фронтенд.
Зависит: шаги 3–4.
Включает:
- иконки колод: не запрашивать картинку, если в реестре нет `icon` (сейчас папка пуста — до 40 запросов с 404 на Winrates);
- кликабельные строки через `<Link>` вместо `onClick` на `<tr>` — доступ с клавиатуры;
- общий компонент состояний загрузки и ошибки (на Events загрузки нет вовсе);
- `preferredColors`: посчитать из реестра колод или убрать колонку.

## Verification
1. После каждого шага: `npm run build`, `npm test`, `npm run check-data` локально и в CI.
2. Снимок цифр из шага 1 совпадает до и после рефакторинга (шаги 2, 4–7); изменения шага 3 просмотрены вручную.
3. Ручной прогон страниц: /events, /event/:id, /players, /player/:id, /winrates.
4. Добавление нового события по новому процессу проходит от входящего файла до страницы.

## Decisions
- Оставляем «git как БД»: JSON-файлы в репозитории, расчёт на билде.
- ID игроков — имя и фамилия латиницей вместо `p01`…`p28`; инициалы остаются сокращениями для ручного ввода (среди 26 игроков инициалы уже совпадают дважды: AM, MB).
- Подтверждено: p02 и p10 — Wiaczasłau Kukhtsiuk, p03 и p11 — Wojciech Ćwikliński. Дубли возникли при импорте из-за разного написания имени (`Wiachaslau`) и обрезанного имени (`Wojciech Ć...`).
- `Marek Pałub...` — полное имя неизвестно (не влезло в стендинги). ID `marek-palub`, имя хранится как есть; когда полное имя станет известно, меняется только `name`.
- Старые ссылки при смене ID (игроков или событий) не сохраняем: редиректы не делаем, игрока или событие можно найти заново.
- Порядок изменён относительно первичного анализа: единый источник данных идёт до реестров, чтобы миграция данных шла в одном месте, а не в двух.
