# Trojmiasto Premodern Notes

Detailed project operations and data workflow notes.

## Implemented

- Events list page with click behavior from the specification.
- Players list page.
- Player detail page with overall winrate and favorite deck.
- Event detail page with dynamic round columns.
- Decks tab as placeholder for next iteration.
- Event-first data model: one JSON file per event in `data/events/`.
- All derived data is generated before `dev`/`build` and in CI; it is not committed.

## Data layout

- `data/events/` — one JSON file per event, the single source of truth
- `data/players.json` — registry of players: `{ id, name, aliases? }`; the id is the name in latin letters (`marcin-kowalski`)
- `data/incoming/` — drafts of new events before import
- `data/templates/` — starter templates for new event files
- `public/data/` — generated by `npm run generate-data` (`events.json`, `cache/players.json`, `cache/matchups.json`, ...); not committed, rebuilt before `dev`/`build` and in CI

## Data flow

1. Source of truth: event files in `data/events/` (one file per event).
2. Event files may omit `name` (defaults to `<place> <type>`) and `mode` (defaults to `roundByRound`).
3. New events are drafted in `data/incoming/` from `data/templates/` and imported with `add-event` / `add-event-compact`, which write the event file.
4. `npm run generate-data` builds `public/data/events.json` and `public/data/cache/*` from the event files.
5. Generation runs automatically before `npm run dev` / `npm run build` and in CI; generated files are not committed.

## Add New Event (recommended flow)

### Compact flow (round-centric JSON)

Use this flow when source data is organized by rounds, not by players.

1. Copy template:

```bash
cp data/templates/new-event.compact.template.json data/incoming/incoming-2026-08-10.compact.json
```

2. Fill compact file with:
- `place` and `type` (`name` is optional and defaults to `<place> <type>`).
- `rounds` object where keys are round numbers (`"1"`, `"2"`, ...).
- Each round contains array of entries:
  - Match: `{ "player1": "A", "player2": "B", "result": "2-1" }`
  - Bye: `{ "player": "C", "result": "bye" }`
- `standings[]` rows with required `localId`, `rank`, `points`, `deck`.

3. Player mapping rules in `standings[]`:
- Known player: provide `playerRef` (or `playerName`; script auto-resolves known names).
- New player: provide `playerName`; importer assigns temporary compact `playerRef` and final stable `playerId` is generated by normalizer.

4. Validation:
- Importer checks mirror pairings and BYE constraints via regular validation.
- Importer checks that each `standings[].points` equals points calculated from rounds.
- Default scoring is win=3, draw=1, loss=0, bye=3, id=1.
- Optional override is available via `scoring` block in compact file.

5. Run:

```bash
npm run add-event-compact -- --file data/incoming/incoming-2026-08-10.compact.json --dry-run
npm run add-event-compact -- --file data/incoming/incoming-2026-08-10.compact.json
```

Event id is optional in incoming files.
- If `id` is omitted, `add-event` generates it automatically from `date + name`.
- If generated id already exists, script appends numeric suffix (`-2`, `-3`, ...).
- If an event with the same date, place and type already exists, `add-event` / `add-event-compact` stop, so the same event is not imported twice. For a genuinely different event on the same day, add `--allow-same-day`.

1. Copy template and fill it:

```bash
cp data/templates/new-event.template.json data/incoming/incoming-2026-07-15.json
```

2. Validate and add the event (creates a file in `data/events/`):

```bash
npm run add-event -- --file data/incoming/incoming-2026-07-15.json
```

Notes about `playerId`:
- Preferred for repeat players: use `playerRef` instead of retyping full name.
- `playerRef` can be existing `playerId`, full player name, or common alias (for example initials like `wk`).
- In incoming/template files you can omit `playerId` completely.
- For known players, `playerName` can also be omitted if `playerRef` or stable `playerId` is provided.
- If you use temporary IDs like `player-a` / `player-b` (or `auto`), script will auto-resolve IDs.
- If `playerName` already exists in the dataset, existing ID is reused automatically.
- For new names, the script creates an id from the name in latin letters (`Paweł Łoś` -> `pawel-los`, `-2` for a namesake) and adds the player to `data/players.json`.
- If a new player name looks truncated (ends with `...` or `…`), the script warns: check it is not an existing player first.
- If an alias is ambiguous (for example initials `AM` fit two players), the script stops and lists the candidates; use the player id, the full name, or add an alias to `data/players.json`.

Notes about round opponents:
- Recommended: use text `localId` in standings and `opponentLocalId` in rounds (event-local references).
- Example: player `{ "localId": "pB", ... }` can be referenced as `"opponentLocalId": "pB"`.
- Numeric local IDs are also supported for backward compatibility.
- You can also use `opponentPlayerRef` in rounds (same rules as `playerRef`).
- You can set `opponentPlayerName` in each round instead of `opponentPlayerId`.
- Script will resolve it to `opponentPlayerId` automatically when possible.
- If opponent is unknown at the moment, you can leave `opponentPlayerId` omitted (it becomes `null`).

Notes about dropped players:
- Players can have different number of rounds.
- If player drops, simply omit missing rounds for that player.

Notes about special round results:
- `resultType: "BYE"`: counts as match `1-0-0`, game `0-0-0`.
- `resultType: "ID"`: counts as match `0-0-0`, game `0-0-0` (does not affect played games).
- If `resultType` is omitted, default is `PLAYED` and regular `match` record is expected.

Notes about round records:
- For `PLAYED` rounds, preferred input is only `game`.
- `match` is derived automatically from `game`:
  - `game.wins > game.losses` -> `1-0-0`
  - `game.wins < game.losses` -> `0-1-0`
  - `game.wins == game.losses` -> `0-0-1`
- `BYE` and `ID` set round match/game automatically by special rules.

Notes about standings totals:
- `standings[].match` and `standings[].game` are auto-calculated from `rounds` on add/update.
- In incoming/template files you can omit standings totals and keep only round-level data.

Standings-only mode (no round details available):
- Set event `"mode": "standingsOnly"`.
- In this mode `rounds` are optional and round pairing validation is skipped.
- You must provide `standings[].match` and `standings[].game` explicitly.

Example standings-only row:

```json
{
  "rank": 1,
  "playerRef": "wiaczaslau-kukhtsiuk",
  "points": 12,
  "deck": { "name": "Replenish", "colors": "WU" },
  "match": { "wins": 4, "losses": 0, "draws": 0 },
  "game": { "wins": 8, "losses": 2, "draws": 0 }
}
```

3. Optionally regenerate site data to preview it (`npm run dev` and `npm run build` do it automatically):

```bash
npm run generate-data
```

4. Quick validation + build:

```bash
npm run check-data
npm run build
```

5. Commit only the new event file from `data/events/`. Generated files in `public/data/` are not committed.

Dry run mode is available:

```bash
npm run add-event -- --file data/incoming/incoming-2026-07-15.json --dry-run
```

If you want to remove incoming file automatically after successful append:

```bash
npm run add-event -- --file data/incoming/incoming-2026-07-15.json --delete-source
```

## Fix Existing Event

Use this flow when you need to correct player name, deck name, points, or match/game results.

1. Edit the event file directly, for example `data/events/sidequest_21.09.2026.json`.

2. Validate the edit (dry run):

```bash
npm run update-event -- --file data/events/sidequest_21.09.2026.json --dry-run
```

3. Apply: re-normalizes the file in place (resolves players, recalculates standings totals from rounds):

```bash
npm run update-event -- --file data/events/sidequest_21.09.2026.json
```

4. Check, then commit the event file:

```bash
npm run check-data
```

`update-event` uses the same player ID normalization rules as `add-event`.

## Players registry

`data/players.json` lists every player once: `{ "id": "marcin-kowalski", "name": "Marcin Kowalski", "aliases": ["Marcinek"] }`.

- Event files reference players by `playerId` / `opponentPlayerId`; `check-data` fails on an unknown id.
- The name shown on the site always comes from the registry; `playerName` in event files is informational.
- Aliases from the name are automatic (full name, first name, first + last name, initials); `aliases` adds extra ones.
- To fix a name, edit `name` in the registry. To change an id (for example when a full name becomes known):

```bash
npm run rename-player -- marek-palub marek-palubski --name "Marek Pałubski" --dry-run
npm run rename-player -- marek-palub marek-palubski --name "Marek Pałubski"
```

The script updates the registry and every event file; old links to the player's page stop working.

## Before GitHub Pages deploy

1. Add or update event via `npm run add-event -- --file <event-file>.json`.
2. Run `npm run check-data`.
3. Verify locally in browser (`npm run dev`).
4. Run `npm run build`.
5. Commit the event files; generated data is rebuilt in CI.
